# Review of the Agent code after the Harness Implementation

This product is evolving from a pilot towards being a production-ready version. The harness works, but the agent code takes structural shortcuts that are not fit for a PR.

This is from reviewing the agent implementation:

1. **The backend's routes are spread across three modules.** The base URL is in one place, `agent/api.py`, and that is good. But `tools.py`, `claim.py` and `queue.py` each build their own API paths: 18 call sites for 15 backend operations, most with the `path()` helper and four as raw strings (`"/api/claims"`, `"/api/runs"` and `"/api/instructions"` twice). `path()` lives in `tools.py`, so `claim.py` and `queue.py` import a URL helper from the tools module. Every module that talks to the backend has to know its routes.
2. **`api.py` is a transport, not an API client.** It should hold one named function for each backend operation the agent uses, such as `get_claim`, `start_claim`, `release_claim`, `add_step`, `create_run`, `write_todos` and `finish_run`, with every path in this one module. `dashboard/src/api.ts` already works this way, and the agent should match it. The split between `call()` (a refusal stops the run) and `tool_reply()` (a refusal goes back to the model) is deliberate and stays. Also, `queue.py` reaches into `claim.py` for `messages()`, a stream helper that has nothing to do with claims.
3. **The harness is spread out and mixed with UnderCover domain specifics.** The agent harness and the tools should be cleanly separated from the business logic and easy to understand.
   - Tools are in two places: the claim agent's in `tools.py`, the queue agent's (`list_claims`, `write_todos`, `work_claim`) in `queue.py`.
   - State reaches the tools and the middleware through closures: `tools_for(claim_id)`, `tools_for_run(run_id, cap, taken)` and `check_for_missed_claims(taken, cap)`. LangChain 1.x has a built-in way to pass state: `create_agent(..., context_schema=RunContext)`, with tools taking a `runtime: ToolRuntime[RunContext]` argument and middleware reading `runtime.context`. The runtime argument is hidden from the model's tool schema, so the model still passes no record ids, which was the reason for the closures. With that, all the tools sit together at module level in `tools.py`.
   - `create_agent`, its middleware and the stream are built twice, in `claim.work` and `queue.work`, each surrounded by domain rules: report lines, releasing a claim, refusing a claim over the cap, finding missed claims. The harness should be in a module like `harness.py`, and `retry()` in `model.py` belongs there too. `claim.py` and `queue.py` keep only UnderCover's rules.
   - `queue.py` mixes tools, middleware, cap rules and the agent loop in 165 lines. The entry points `work_queue` and `run` are short; the module around them is not.
   - `claim.work` passes a `thread_id` in the config, but the agent has no checkpointer, so it has no effect.
4. **Both instructions are long, step-by-step, prescriptive scripts.** `backend/instructions/claim.md` is 12 numbered steps, `backend/instructions/queue.md` is 6 numbered steps with sub-cases. This is not a good approach for agentic AI. An agent should have a goal, not a series of fixed workflow steps, otherwise we would just write code instead. Rewrite each as the goal, the rules that bind it and what a good result looks like. Keep the rules: when to approve, decline or refer, and to refer only for those reasons; how the payout is worked out; a decision counts only once `decide_claim` records it; a payment held for sign-off over $1,000 is expected; summaries in plain text; the queue agent never decides a claim itself. Leave out what the tools' descriptions already say and what code already enforces, such as step 5 of the queue instructions, which repeats the check for missed claims that the `after_model` hook makes certain.

Please follow these steps:
- Confirm that these issues exist, and determine how this was allowed to happen.
- Fix the issues. Keep the behavior as it is: the same tools, middleware and report lines.
- Investigate whether similar issues exist in the backend and dashboard code. Candidates from this review: `backend/runs.py` holds a claim's steps and `run_agent`, while `backend/queue.py` holds the runs (`/api/runs`), so the module names don't match what is in them; and both import the agent directly to start it in a background task. I want clean, idiomatic code, suitable for a PR.
- Retest after fixing: `npm run check`, then, after reseeding, a live run capped at five claims on the default model, as `docs/HARNESS.md` asks.
- Update PROCESS.md and CODE_STANDARDS.md and STATUS.md so that this never repeats, and let me know how you did that.
